# 45. Reader-Credible Serial Generation（读者可信的连续叙事）Q1 规格

> 建立：2026-08-10 ｜ 目标：把项目从 T0/Q0 推进到 T0/Q1 ｜ 状态：规格冻结，分阶段执行
> 本文件是仓库可提交的 Q1 规格；逐阶段需求/设计/任务/进度记录在本地 `.taskflow/active/reader-credible-serial/`（不入库）。

## 1. 背景

系统当前已具备「能完成流程」的能力（Q0：生成、审查、落盘、继续运行），但存在一类结构性缺陷：

1. 正文审查只注入「本章正文」，不审查相邻章节组成的连续文本；
2. 正文提交后保存的是生成前规划出的 `objects + plotunit + new_state`，不是从正文重新提取并核对后的状态。

这一缺陷是「已找到的人物后来重新失踪」这类连续叙事断裂能够发生的结构性条件。本计划把质量轴
与部署 Tier 分离（Tier 0/1/2 是部署成熟度，Tier 1 已定义为 DirectAPI，不能占用），
新增一条正交的叙事质量轴：

| 质量级别 | 定义 | 当前状态 |
|---|---|---|
| Q0 流程有效 | 能生成、审查、落盘、继续运行 | 已达到 |
| Q1 读者可信 | 连续事实可信、人物不变形、每章有新进展、原有阅读快感不漂移 | 本计划目标 |
| Q2 出版候选 | 长程质量稳定，并通过目标读者和人工编辑校准 | 后续阶段 |

## 2. 目标架构

系统必须具备三种能力：

1. 知道什么时候不该继续写；
2. 写完以后，以实际正文而不是写作计划更新世界；
3. 不仅检查「有没有错」，还检查读者为什么愿意继续读。

```mermaid
flowchart LR
    A["真实原文或 WorkSpec"] --> B["读者契约 + 可信状态"]
    B --> C["续写可行性判断"]
    C -->|"故事已闭合"| D["停止 / 请求新前提"]
    C -->|"存在有效下一步"| E["候选 PlotUnit"]
    E --> F["章节草稿"]
    F --> G["从正文提取事实与状态变化"]
    G --> H["跨章硬一致性门禁"]
    H --> I["章节读者体验门禁"]
    I --> J["三至五章连续阅读门禁"]
    J --> K["提交正文 + 更新状态 + 推进 Frame"]
    K --> B
```

**核心原则**：PlotUnit 是写作意图，正文才是最终事实；状态只能根据通过审查的实际正文更新。

## 3. 四项核心改造

### 3.1 续写可行性门禁（ContinuationViabilityUnit）

在生成 PlotUnit 之前回答：原故事是否已完成主要情感闭环；是否仍有真实的外部冲突、未完成选择或
未兑现承诺；下一章能否产生新的状态变化；继续写是在打开新故事，还是重新解释已经结束的故事；
如果不能继续，需要什么新前提才能重新启动。

输出区分：`continue`（存在有效下一状态）/ `needs_premise`（必须由操作者提供新冲突或新阶段目标）/
`stop`（当前故事应结束，不生成章节）。

### 3.2 正文事实包（ProseEvidencePackage）

从待提交正文提取：明确陈述的事实；人物所在地点、时间与在场关系；人物知道了什么、不再相信什么；
道具的身份和状态；角色关系变化；作出的选择及可见后果；新增/推进/兑现的承诺；本章真正发生的
状态变化。每项结论必须携带正文证据片段。

随后两次核对：
1. PlotUnit 预期变化 ↔ 正文实际变化；
2. 正文实际变化 ↔ 上一可信状态和相邻章节。

不受正文证据支持的状态不得写入；正文新增 PlotUnit 之外的关键事实则阻断，不能静默吸收。

新增模块：`src/object_state/prose_evidence.py`、`src/workflow_action/prose_evidence.py`、
`src/workflow_action/prose_reconcile.py`、`src/boundary_control/chapter_commit.py`。
修改：`src/extend_short_form.py`、`src/compose_short_form.py`、`src/boundary_control/runtime_state.py`。

### 3.3 读者契约（ReaderContract）

现有组件已分别回答：StyleProfile（怎么写）、AuthorKernel（为什么选这条剧情）、
ReaderExpectation（读者在等哪些答案）、SceneExperience（场景如何被读者感受到）。缺少一个总规格：
**读者为什么选择这本书，而不是另一本书**。

ReaderContract 逐作品声明：目标读者；核心阅读快感（限制 2–4 项）；主角值得持续跟随的理由；
作品的核心张力；合理的章节推进速度；必须保留的叙事声音和关系动力；禁止出现的漂移；
哪类结尾算有效钩子；哪些情形意味着故事应结束；新开首章必须交付的最小承诺。

写成中性机制而非作者模仿（如：伤感必须被粗粝笑料和具体生活细节抵消；商业主角必须通过具体判断和
行动展现聪明；「代价」必须由人物选择触发，不能只作为设定说明）。

新增模块：`src/object_state/readercontract.py`、`src/workflow_action/reader_contract.py`。
继续复用而不替换：ReaderExpectation、SceneExperience、StyleProfile、AuthorKernel。

### 3.4 读者门禁（ReaderQualityGate）

不破坏现有 `ReaderExperienceReport`（其 `route=none`、不阻断的定义不变），新增 `ReaderQualityGate`
消费现有报告与新的连续阅读报告：

- **单章门禁**：主角是否有欲望、阻碍和选择；是否真的发生新事件；情绪是否由场景产生而非作者解释；
  对白是否属于具体人物；章末是否形成真实问题；是否偏离 ReaderContract。
- **相邻章门禁**：上一章已回答的问题是否被重新提问；人物/道具/时间/地点是否被无事件重置；
  是否重演上一章已完成的场景；是否出现「上一章末」「本章」等编辑/生成过程文字；
  开头是否在机械复述上一章结尾。
- **三至五章窗口门禁**：是否连续反复使用同一顿悟；是否多章只推进心理总结而无外部变化；
  是否反复使用同一种结尾结构；ReaderExpectation 是否真正推进；主角解决问题方式是否越来越单一；
  原作阅读快感是否被生成文本自身逐步稀释。

门禁策略：客观连续性错误 → `block`；正文层可修问题 → `rewrite` 后重新提取正文事实并复核；
三章窗口出现重复闭环 → 阻断下一章，要求重新规划 PlotUnit；主观审美分歧 → 明确人工决定点，不静默放行。

## 4. 版本化运行与污染隔离

固定 `output/<mode>/` 易让旧响应、旧状态和失败正文污染后续运行。Q1 改为显式版本化：

```text
output/<mode>/
├── runs/<run_id>/{manifest.json,prompts/,responses/,drafts/,evidence/,gates/,state/}
├── current_run.json
└── failed_quality_baselines/
```

规则：
- 升级为 `flow_version=3`；旧版工作区不得被静默兼容，提供显式迁移命令；
- 每个运行记录原文哈希、前章哈希、草稿哈希、事实包哈希、状态前后哈希；
- `commit manifest` 最后写入；下游只消费有完整提交标记的运行；
- 失败运行保留，但永远不能成为下一章上下文。

**新的提交次序**：Draft → Post-Prose Review → ProseEvidence 提取 → 跨章 Reconcile → Reader Gate
→ 准备正文/状态/Frame/台账 → 写入 commit manifest → 整体成为 Committed。
任一步失败：不写 `chapters/`；不推进 Frame；不更新 FactLedger/CharacterModel/ForeshadowGraph；
不消费成有效历史；原始错误完整暴露，不走替代方案。

新增模块：`src/boundary_control/run_manifest.py`、`src/boundary_control/chapter_commit.py`。
CLI 新增/扩展：`novel migrate <name> --to-flow 3 --preserve-old`、`novel inspect-run <name>`、
`novel reader <name> --window 1|3|5`、`novel gate <name>`（同时报告结构、连续性和读者质量状态）。

## 5. 实施阶段与门禁

| Phase | 主题 | 门禁 |
|---|---|---|
| 0 | Q1 质量基线 | 现有流程会错误放行 8 类合成夹具 |
| 1 | 正文事实与跨章硬一致性 | 失败夹具全部无法提交；失败后正文目录/Frame/状态哈希不变 |
| 2 | 事务式提交与版本化运行 | 无半提交（正文已存在但状态未更新，或反之） |
| 3 | 续写可行性与读者契约 | 已闭合样本必须返回 stop 或 needs_premise |
| 4 | 单章与滑动窗口读者门禁 | 重复闭环第二次即阻断；连续三章不得重复完成同一心理结论 |
| 5 | 三条现有内容的恢复 | 见 §6 |
| 6 | 验证、校准和发布 | Q1 发布门槛（§7） |

### 合成夹具（Phase 0，脱敏）

1. 票根在下一章变成花瓣（道具身份变化）；
2. 已找到的人重新变成失踪（状态回退无事件支撑）；
3. 一月之后又回到十二月（时间回退）；
4. 六十年周期却隔十一年再次到期（时间算术错误）；
5. 第 N 章末等元文本泄漏；
6. 两章以相同句子和相同场景开始；
7. 已完成顿悟连续三章重新完成；
8. 当前章没有有效状态变化。

### Phase 1 关键实现点

- ProseEvidencePackage 每个事实必须携带正文证据；
- 对接 FactLedger/CharacterModel/ForeshadowGraph/TimeBook；
- 时间单位与显式算术检查；人物关系、道具身份、生死状态检查；元文本泄漏和章节编号检查；相邻章状态差分；
- 合法的时间跳跃、回忆和不可靠叙述需要显式标记才能通过。

## 6. 三条现有内容的恢复（Phase 5）

所有旧正文先做哈希和可恢复备份，再移出活动 `chapters/`；不原地修改。

### 《续写作A》——可信边界：第 23 章

先执行可行性判断：若为 `stop`，接受「正确续写是停止」；若要继续，必须先批准新的外部冲突、时间跨度
和人物目标。不允许再次围绕同一通电话和同一顿悟展开。第一轮只生成一章；通过后再做三章窗口，不直接补齐八章。

### 《续写作B》——可信边界：第 1196 章

1. 从原始可信正文重新 Rebuild，不复用 1197–1205 产生的状态、ChoiceLedger 或 AuthorKernel 增量；
2. 生成新的 1197 章；重点锁定：票根、角色甲恢复阶段、角色乙状态、建邺人事、时间日期；
3. 单章通过后生成三章，三章通过后扩展到五章；五章窗口必须展示具体商业行动，不能只靠电话、棋、牌、桌等抽象词推进。

### 仙侠新作

现有第一章作为失败基线，不原地修补。重生成前必须先解决故事前提：
- 推荐保留「一甲子一期」；
- 将师父十一年前离开改为提前偿债、调查旧债或另有原因；
- 不能再称十一年前为「上期届满」。

首章 Q1 要求：阁使钩子保留；沈砚必须在章内作出一个定义人物的主动选择，且该选择立即产生代价；
至少一个细节必须具有作品独有性，而非通用仙侠设定；第二章不能主要用于阁使解释规则。

## 7. 验证、校准与 Q1 发布门槛

### 自动测试
- 新模型和生命周期单测；相邻章矛盾集成测试；run manifest 崩溃恢复测试；
  compose/extend 共同门禁测试；隐私红线测试；flow v2→v3 显式迁移测试；
- 全量 pytest；`python scripts/tier0_canary_regression.py`；三流 `novel gate`。

### 连续生成 Canary
- 仓库内合成无版权文本：compose 连续 5 章；extend 连续 5 章；
  resolution 结束样本必须停止；时间跳跃与不可靠叙述样本正确处理。
- 本地私有 Canary：官路至少连续 5 章；仙侠至少连续 3 章；万物得到可信的停止或新前提判断。

### 人类读者校准（隐藏来源连续阅读）
不展示系统自评，读者只回答：是否愿意翻下一章；人物是否还是同一个人；何处开始走神；
是否有读不懂或不相信的事实；本章真正发生了什么；最期待的下一件事是什么。
首轮阈值作为试运行数据，不预先伪造精确科学指标。

硬标准：零事实/时间/关系/道具矛盾；零生成过程文字；零无事件状态重置；
多数目标读者愿意继续；没有多数读者认为核心人物或作品类型已经改变。

### Q1 发布门槛（全部满足才声明 T0/Q1）
- 现有完整测试基线无回归；三流 Canary 通过；合成失败夹具全部被正确阻断；
- 两条可继续流程完成连续窗口验证；停止型流程能拒绝无意义续写；
- 本地真实作品信息未进入 Git；生成仍保持 operator-in-the-loop；
- 不调用 Provider，不引入闭环自动化；
- 创建独立 Q1 证据记录和不可变 Git 标签，不改写 `v0.1.2-tier0`。

## 8. 明确不采用的方案

- 不只给 Review prompt 多塞一章正文（能缓解接缝，不能解决正文与状态脱节）；
- 不只增加重复句式检测（抓得到表面 AI 味，抓不到人物、因果和阅读快感）；
- 不手工修补当前 17 章（会留下污染状态，也不能防止复发）；
- 不让 ReaderReport 继续只做参考（质量报告不能影响提交，就不是生产门禁）；
- 不用特定作者模仿作为续写标准（保护的是作品的阅读机制，不是复制个人笔法）；
- 不保证每次都产出正文（能够正确停止是续写系统成熟的重要标志）。

## 9. 主要风险及控制

| 风险 | 控制办法 |
|---|---|
| 读者门禁过于主观 | 客观错误硬阻断；审美问题先 rewrite，再进入显式人工决定 |
| Prompt 膨胀 | 一章完整正文 + 三章事实差分 + 五章摘要，不无限追加原文 |
| 正文事实提取产生幻觉 | 每条状态更新必须有原文证据锚点，无证据不写入 |
| ReaderContract 变成套话 | 限定为可观察的阅读机制和禁例，必须由真实样本校准 |
| 系统变得不敢写 | 使用 needs_premise，由操作者提供新阶段目标，而非静默失败 |
| 旧状态污染新运行 | flow v3、独立 run_id、显式迁移、哈希与提交标记 |
| 只对三个样本过拟合 | 私有样本只做 Canary；正式测试使用多种合成扰动 |

## 10. 实施顺序与批准点

严格按顺序执行：Phase 0 → 1 → 2 → 3 → 4 → 5 → 6。

批准点设置在：Q1 需求与架构设计完成后；flow v3 数据迁移前；移动现有失败正文前；
真实作品重新生成前；创建 Q1 标签前。
